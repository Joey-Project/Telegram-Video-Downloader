# 合集下载消息与执行轮次

## 摘要
- 完整执行一轮合集任务时，只创建一条合集主消息和每个所选视频的一条状态消息；后续进度、处理、校验与终态更新对应消息。
- 恢复和手动失败重试开启新的 generation（同一任务的新执行轮次），保留旧轮消息。网络和 File Provider 的内部重试不另开轮次。
- 已存在且通过核验的所选视频也有一条跳过下载状态消息；取消时不为尚未开始的视频补发消息。

## 实现
- 合并合集主消息，并记录每个视频的消息 ID；开始下载、进度、处理、发布校验与终态编辑同一条消息。
- 通过持久化轮次保护，阻止旧轮进度、完成记录和取消清理覆盖恢复后的新轮状态。旧队列记录默认使用第零轮。
- 每轮的视频消息关联仅在进程内保存；轮次与合集主消息关联沿用现有队列记录持久化，不引入额外 JSON 文件。
- 已确定合集的 File Provider 内部重试保持消息数量不变。
- Bilibili 短链接在解析目标前的队列重试同样不新增提示；进度读取遇到临时 File Provider 错误时等待并重验轮次，不丢弃该轮事件。
- 文件已校验且完成记录已保存后，历史记录搬移失败仅在主消息中提示，视频保持已验证；终态读取也会重试临时 File Provider 错误。
- 合集主消息的终态编辑遇到临时失败时，最多重试三次，始终复用同一消息 ID，并在每次尝试前核对轮次。
- 每个视频的已验证、失败和取消终态编辑同样最多重试三次；每次重试核对轮次，始终编辑原视频消息，不补发消息。
- 详情分页与主消息终态更新共享稳定的编辑锁；终态先写入最新详情视图，迟到的运行中分页编辑结束后再投递最终主消息。完成后仍可翻页，始终显示最终状态。
- 所有已选视频都已存在时，下载器在提前返回前仍发送完整合集清单，创建逐视频跳过状态并保留主消息中的详情分页。
- 选择提示的发送结果、失败处理及按钮回调同时核对轮次与等待状态，旧提示不能改写、取消或重新排队恢复后的任务。
- 通用队列按钮也携带轮次，并在同一队列操作锁内核对任务、聊天和有效状态；旧按钮只提示刷新队列。
- 取消令牌按轮次绑定，在核对已排队状态的同一操作内注册；取消保存后通知锁内捕获的原令牌，避免漏通知或误通知新轮次。
- 下载操作返回后立即释放下载并发许可，再进行终态读取重试与进度投递收尾；存储暂不可读时不占用下载槽位。
- 选择/去重提示的消息关联遇到临时 File Provider 错误时重试保存，避免另发合集主消息；排队消息编辑期间取消后仍收敛到同一主消息的取消状态。
- 确认更新后的下载计划时，在状态保存成功后退休旧执行的取消令牌；同一轮次的新执行使用独立令牌，旧执行收尾不能移除它。

## 验证范围

- 真实 Telegram 和真实媒体下载未作为本次本地验证执行。
